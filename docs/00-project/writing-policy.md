## STYLE-001: Language and notation
Use English for documentation, code identifiers, comments, commits, PR descriptions, UI copy and prompts. Use technical, specific wording. Define domain terms before relying on them. Preserve exact external identifiers and necessary quotations with attribution.
Do not use emojis, em dashes, en dashes as punctuation, decorative Unicode symbols, or ornamental separators. Use standard punctuation, ordinary hyphens, Markdown lists, and code notation. Diagram syntax and mathematical operators required to express a contract are permitted; decorative symbols are not.

## STYLE-002: Claims and tone
State the behavior, constraint, decision, or measured result directly. Avoid cliches, marketing superlatives, slogans, generic excitement, artificial corporate language, and unsupported claims. Do not use phrases such as "Thrilled to announce", "Excited to share", "Revolutionary", "Game changer", or "Leveraging the power of" in project prose. They appear here only as prohibited examples.
Use first person for public learning narratives, with one concrete technical idea per post. Explain necessary terminology for nontechnical readers without removing the actual tradeoff.

## STYLE-003: Evidence and review
Distinguish proposed, implemented, tested, and accepted work. Name limitations and use measured values only with a reproducible source. Review English, terminology, prohibited punctuation, and claims before completion. Automated style checks can detect punctuation, not certify language quality or factual accuracy.
This file is the canonical writing rule. AGENTS.md and communication documents reference it rather than creating variants.
